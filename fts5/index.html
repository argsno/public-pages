数据库内核解剖 · 全文索引

SQLite FTS5全文索引的设计与实现 · 源码级解剖 + 本机实测

FTS5 是把一台段式倒排索引引擎塞进单个 .db 文件的插件：写入先在内存里攒词、提交时排序落成一个不可修改的段，查询时用「竞赛树」把多个段归并成一条有序结果流，空闲时再按 LSM 式策略把段吃掉。本页把它的字节格式、合并策略、查询计划和分词器全部拆开，每个数字都由本机 SQLite 3.53.4 实测得出。

结论速览

  • 结构：一张虚拟表 + 5 张影子表；%_data 里装着全部倒排索引，它的 rowid 把「段 id / 页号」编进一个整数。
  • 格式：段叶页 = 4 字节页头 + 词条/文档列表 + 页尾偏移表；行号做差值编码，词条做前缀压缩，页尾偏移做增量压缩，全是 SQLite 变长整数。
  • 写入：一个事务在内存哈希里攒词，提交时排序落成新段——所以批量提交比分条提交快 200 倍以上（实测 0.092 s vs 20.10 s）。
  • 查询：每个词元一个迭代器，所有段并行归并，用擂台树取最小行号；短语靠位置列表验证相邻性，前缀查询按字符长度挑前缀索引。
  • 打分：内置 bm25（k1=1.2, b=0.75），返回负分；本页手算结果与 SQLite 输出逐位一致，IDF ≤ 0 时被钳到 1e-6。
  • 取舍：位置信息值 4 倍索引体积；前缀索引值 2.4 倍体积换短前缀提速；中文默认分词是坑，要用 trigram。

01它解决什么问题

用 LIKE '%词%' 找文本要读全表；FTS5 用「词元→文档」的反查表把这件事变成一次索引跳读。

代价交换得很清楚：写入时多维护一份索引，换取查询时不用读正文。下面是三种「找文本」的方式在同一份语料（5,778 篇、3.30 MB 正文）上的实测：

怎么找代价（本页实测）能回答的问题
LIKE '%ship%'逐行读正文、逐字节比较4.900 ms（5,778 篇全表扫描）能：任意子串。命中 563 篇
LIKE + trigram 索引把 3 字符组合建成倒排索引后回表验证索引体积×3.7（实测 2.49 → 9.21 MB）能：≥3 字符子串。LIKE 自动走索引
MATCH 'ship'倒排索引直接给出行号列表0.140 ms（命中越多越慢，但不用读正文）不能：子串。命中 359 篇（完整词元）
MATCH 'ship*'同一倒排索引里的词条区间扫描0.210 ms（前缀加速见第 06 节）能：词元前缀。命中 448 篇
三者不是替代关系，而是三种语义：MATCH 'ship' = 359 篇（只认完整词元）、 MATCH 'ship*' = 448 篇（词元前缀）、LIKE '%ship%' = 563 篇（任意子串，含 warship）。要子串又不想全表扫描，就用 trigram 分词器给 LIKE/GLOB 建索引。

它和 Lucene 是同一族

FTS5 不索引「文档」，而是索引「一次提交写入的一批词条」，这个单位叫段；查询时把若干段归并成一个有序流。这套「不可变段 + 后台合并」的骨架，和 Lucene/Elasticsearch 是同一个设计传统：

03存储全貌：一张虚拟表 + 5 张影子表

FTS5 是虚拟表模块（sqlite3_module），自己不拥有文件格式——它把索引全部写进普通 SQLite 表里。

创建 CREATE VIRTUAL TABLE demo USING fts5(title, body) 之后，sqlite_master 里会多出 5 张以表名为前缀的 影子表（shadow tables）——它们就是普通表，可以直接 SELECT，这也是本页所有「解剖」得以进行的原因：

影子表建表语句作用本页 demo 体积

<t>_contentid INTEGER PRIMARY KEY, c0, c1 …正文副本；只有默认模式才有（contentless / external content 没有）3.28 MB
<t>_docsizeid INTEGER PRIMARY KEY, sz BLOB每行每列的 token 数（变长整数序列），bm25 算 D 用；columnsize=0 时不存在12 KB
<t>_idxsegid, term, pgno前缀索引词条清单（每个段哪些前缀词，落在哪一页）48 KB
<t>_configk PRIMARY KEY, v版本号 4 与运行时配置（automerge / crisismerge / hashsize …）< 1 KB

%_data 的行号是一个打包的位域

倒排索引不是独立文件，而是 %_data 这张表的若干行。id 这个整数被按位切分存储「哪个段的第几页」，由宏 fts5_dri() 生成，位宽写在 fts5_index.c 里：

位段（bit 从高到低）宽度含义
30..0 页号31 位段内第几页，从 1 开始；上限 FTS5_MAX_PGNO = 0x7FFFFF00
35..31 索引树高度5 位doclist 索引（dlidx）自己的层数，最多 32 层
36 文档列表索引位1 位1 = 这一行是 doclist 索引页，0 = 段叶页
52..37 段 id16 位段编号，1~65535，删除后 id 可复用
53 墓碑页位1 位1 = 墓碑哈希页；只在 contentless_delete=1 的表里出现
63..5410 位空着不用——保证 rowid 是正数（bit63 是符号位）

各字段的宽度不是随手定的，源码里就是四个独立常量（FTS5_DATA_PAGE_B=31、HEIGHT_B=5、 DLI_B=1、ID_B=16）。为什么页号是 31 位？三个理由：

  • 够用且不浪费：31 位 = 2,147,483,648 个页码；按默认 4050 字节的叶页算，单个段最多约 7.9 TB。源码注释直接写着「不可能造出这么大的库」，所以再宽纯属浪费位。
  • 它要能装进 C 的 int：源码把页号存在 int pgnoFirst / pgnoLast / iLeafPgno 里， 31 位（≤ 0x7FFFFFFF）刚好保证按位取出后永远是正数；32 位就会有符号问题。
  • 高位留空双保险：整包只用了 54 位，63..54 空着，bit63（符号位）永远是 0， rowid 始终为正——对 INTEGER PRIMARY KEY 和 1 / 10 这两个保留小号都很友好；另外页号还有一道哨兵上限 FTS5_MAX_PGNO = 0x7FFFFF00（比 2³¹ 小 256），读到更大的值直接判为损坏。

本页 demo 库里那个 911 字节的段页，id 正是 137438953473： 137438953473 = (1 << 37) + 1，即段 id=1、类型=段叶页、高度 0、页号 1；有序号 1、10 的特殊行留给「平均值记录」和「结构记录」，其余全部是段页与 doclist 索引页。

04写入路径：一次 INSERT 的旅程

写入是「先内存、后段」的两段式；理解了这一条，数据库配置里 90% 的 FTS5 性能问题就都能定位。

  1. 分词：对每一列调用分词器（默认 unicode61），得到词元序列，同时记下每个词元的列号与位移。
  2. 进内存哈希（hashsize，默认 1 MB）：按词元聚合出行号列表与位置列表。释放缓冲区的时机很讲究——只有遇到「行号不递增」或缓冲区超限才刷盘，所以一个事务内的行会攒在一起。
  3. 提交时落段：把哈希表按词元排序，写成一个新的 0 层段，并更新结构记录、平均值记录。段一落盘就不再修改。
  4. 增量合并：每写一定数量的叶页（FTS5_WORK_UNIT=64 页为一个工作单位）就在写路径上顺手合并几段。

第 2 步的「内存攒批」带来了本页最实用的一条实测结论：

提交方式（同一批 4,000 篇）耗时 s段总数各层段数索引 MB说明
一个事务插 4,000 篇0.09254 / 11.92推荐做法
每 100 篇提交一次0.409106 / 3 / 12.00
每篇提交一次20.101100 / 2 / 2 / 3 / 31.99灾难：段多、慢 200 倍
一个事务，但 hashsize=20480.34592 / 0 / 1 / 3 / 31.98哈希太小→事务内提前刷段
一个事务 + automerge=00.089441.93不做增量合并

同 4,000 篇数据，一个事务 0.092 秒、每篇提交一次 20.10 秒（218×）。原因是每篇提交都要把哈希表排序落成新段，而提交越碎、段越多、每次提交后还要触发合并。行号递增的前提也要求按 rowid 顺序写入，否则哈希表会更早刷盘。

坑：automerge、crisismerge、hashsize、pgsz 不能写进 CREATE VIRTUAL TABLE（会报 unrecognized option），必须用配置表写入： INSERT INTO ft(ft, rank) VALUES('automerge', 4);。同理 optimize / merge / integrity-check 也是「往表里插一个特殊字符串」实现的管理命令。

5.3 段叶页格式

一个段由若干固定大小（默认 pgsz=4050 字节）的叶页组成。页里没有分隔符、没有对齐填充， 定位全靠页尾那张增量压缩的偏移表：

两条编码规则是整个格式的核心：

  • 词条前缀压缩：只存「与上一个词元的公共前缀长度」+「新增字节」。所以 an 只需存 common=1, new=1 ——真实字节里 an 的条目只有 01 6e 两个字节的说明部分。
  • 行号差值编码：一个词元的文档列表存「首个行号 + 后续差值」。a 出现在第 1、2、3、5、6 篇里，存的是 1, +1, +1, +2, +1。

每条记录的形态是 词元 + 文档列表，文档列表里每篇文档后面跟着它的位置列表。位置不是「字节偏移」，而是词元序号，并且和列号打包进一个 64 位整数（高 32 位列、低 31 位词元序号）。

5.4 交叉验证：自己解的和 FTS5 自己说的对得上吗

把这一页 65 个词条全部解完，得到 118 条 (词元, 行号, 列号, 词元序号) 记录；再让 FTS5 自己通过 fts5vocab 的 instance 模式输出同一份清单：118 条。两边逐条比对完全一致（(4096, 5, 1, 11)、(a, 1, 1, 2)、(a, 1, 1, 6)、(a, 2, 1, 0) …）。后面的结论都可以放心建立在这套解码上。

5.5 变长整数是什么样

-- 写计数器 731 的变长整数编码（结构记录里真实出现的 2 个字节）
-- 规则：每字节低 7 位有效，最高位 1 表示"还有后续字节"
0x85 = 1000_0101b  →  有后续，取低 7 位 000_0101b = 5
0x5b = 0101_1011b  →  结束，取低 7 位 101_1011b = 91
值 = 5 × 128 + 91 = 731          -- 与解码结果一致（731）

-- 单字节的值最大 127；1 个字节存 doclist 里常见的"行号增量"完全够用
-- 页尾偏移用的也是这套编码，所以页尾能压缩（见第 05 节）

页尾偏移表里用得最多的就是这种 1 字节值（≤127）：本页那个 911 字节的页，65 个词条的偏移表只花了 65 字节，平均每个词 1 字节左右。

5.6 词条的第一个字节：这是哪个索引

真实字节里第一个词条是 05 30 34 30 39 36，解出来是词元 4096，但长度是 5 不是 4 ——多出来的 0x30 是索引标签：'0'（0x30）表示主索引，'1'…'31' 表示第 n 个前缀索引（fts5_index.c: FTS5_MAIN_PREFIX）。所有前缀索引共用同一套段/页机制，只是词条前缀不同，所以 prefix='2 3' 不改变格式，只是往同一批段里多写了一批带标签的词条。

5.7 文档列表索引（dlidx）与擂台树归并

两个容易忽略的结构：

  • doclist 索引：一个词元的行号列表可能横跨几百页（the 这种词）。为了让「跳到某一行号」不用顺序读，每页的第一个行号被单独抄进一棵小 b-tree（FTS5_DLIDX_ROWID），并且只有页数超过 FTS5_MIN_DLIDX_SIZE=4 才建。
  • 擂台树（tournament tree）：查询时要同时归并 N 个段的行号列表。FTS5 没有用堆，而是用一张 aFirst[] 数组把 N 个迭代器两两比较的结果缓存成树：aFirst[1] 永远指向当前最小的那个。每次前进只需沿路径重算 O(log N) 次比较，且没有堆的分配开销。

06查询路径：从 MATCH 到一行结果

查询计划由「MATCH 约束 + rank 约束」驱动；词元先各自拿到行号列表，再归并、再验证。

6.1 一个 MATCH 表达式能写什么

demo 库 6 篇文档上的真实输出（rowid）：

查询语义命中 rowid

6.2 短语是怎么验证的

短语 "database engine" 会先被拆成两个词元，各自拿到行号列表，然后检查同一篇文档里是否存在相邻且顺序正确的位置：源码 fts5ExprPhraseIsMatch() 对每个词元的位置列表做 k 路归并，判断条件就是 iPos + i（第 i 个词元的位置必须比第一个大 i）。位置列表就是为这件事存在的。

实测：同一组词序反过来 "engine database" 命中 0 篇——倒排索引本身无法区分词序，词序完全靠位置列表还原。 NEAR(engine b, 6) 是同一套机制的推广：允许 N 个词元的间隔，默认 N=10。

detail=column 和 detail=none 会丢掉位置信息，于是短语与 NEAR 直接报错： fts5: phrase queries are not supported (detail!=full)。这不是「慢一点」，而是功能不存在。

6.3 前缀查询走哪条路

MATCH 'ma*' 这种查询有两种执行方式：扫主索引里 ma~mb 区间的所有词条，或者直接读「2 字符前缀索引」。FTS5 按字符长度挑选索引（fts5IndexCharlen），挑不到就只能扫。

实测对照（同一份 5,778 篇语料、同一台机器，11 次中位数）：

前缀长度无前缀索引有 prefix='2 3'倍数命中篇数

结论：前缀索引的价值随「前缀越短、区间越宽」而放大。5 字符前缀本来只对应很窄的一段词条，装索引纯属浪费空间。

6.4 归并、去重与删除

遍历一个词元的结果时，所有段（以及所有层）的迭代器同时前进，擂台树每次给出最小的行号；若同一行号在多个段里都出现，较新的段赢（删除标记也在最新段里），老段里那条被跳过。删除不重写老段：DELETE 会往最新段写一条带「删除标记」的记录（位置列表长度的最低位就是标记位），直到某次合并把它和旧记录一起消化掉。

列过滤用花括号语法：MATCH '{body} : whale' 把搜索限制在 body 列，不写列名则两列都搜。实测这份语料里 MATCH 'whale' 命中 1,614 篇，其中 1,611 篇只是书名里带 Whale（Moby Dick; Or, The Whale）——列过滤不是小事。

6.5 bm25：相关度怎么算

FTS5 的 rank 列默认等于 bm25(表名)，返回的是负分（SQLite 约定「小者优先」，所以推荐 ORDER BY rank 而不是 ORDER BY bm25(...)）：

score(D, Q) = Σ IDF(qi) · f(qi,D)·(k1+1) / ( f(qi,D) + k1·(1 − b + b·|D|/avgdl) ) IDF(qi) = ln( (N − n(qi) + 0.5) / (n(qi) + 0.5) ) 若≤ 0 则强制取 1e-6 k1 = 1.2 b = 0.75 （写在 fts5_aux.c 里，不是参数） f(qi,D) = 词元 qi 在文档 D 中的出现次数 |D| = 该行 token 总数（来自 %_docsize） N = 表内行数 n(qi) = 含该词元的行数 avgdl = 全表平均行 token 数最终返回 −score（SQLite 认为"越小越靠前"）

07合并策略：LSM 式分级与「写配额」

段不可修改，只能被合并。什么时候合并、合并多少，由三个阈值和一张写计数器共同决定。

规则很短：

  • 每次提交写完 0 层段后，累加「写过多少叶页」到写计数器；跨过 FTS5_WORK_UNIT=64 页的工作单位，就做一单位的合并工作（源码三行：nWork = ⌊(nWrite+nLeaf)/nWorkUnit⌋ − ⌊nWrite/nWorkUnit⌋，配额 nRem = nWorkUnit × nWork ×层数，然后交给 fts5IndexMerge）。
  • 合并的挑法是「段数最多的那一层」，每次至少并 automerge（默认 4）段，输出到上一层。写完之后还要调用 fts5StructurePromote 把段在层之间挪一挪，让同一层里的段大小可比。
  • 实测的形状是「0 层段小、数量多，高层段大、数量少」：一次事务写入 5,778 篇后， L0 是 4 个 12~20 页的小段，L1 是 3 个 130~266 页的大段。
  • 某一层段数达到 crisismerge（默认 16）时无条件合并，防止查询要归并的迭代器爆炸。段 id 只有 16 位、总段数上限 2000，这也是危机合并存在的原因。
  • optimize 是「把所有段并成一个」的维护命令，按 FTS5_OPT_WORK_UNIT=1000 页一步做，可被打断； merge=N 是「至少并 N 段」的温和版本。

10实战清单

每条都能在上文找到依据。

  1. 批量写、单事务提交：事务内的词先攒在内存哈希里，提交时排序落段（实测落成 0 层 4 段 + 1 层 1 段）；逐条提交让同样数据慢 218×（实测 0.092 s → 20.10 s）。
  2. 按 rowid 递增顺序插入：哈希表遇到行号回退会提前刷盘，乱序写入会多出小段。
  3. 别在 CREATE 里写 automerge/crisismerge/hashsize/pgsz：报 unrecognized option，要用 INSERT INTO ft(ft, rank) VALUES('automerge', 8)。
  4. 大批导入后跑一次 optimize：段数 7 / 4 → 0 / 0 / 0 / 0 / 1，短语查询 0.710 → 0.590 ms；之后如果在意磁盘占用可以 VACUUM。
  5. 长文本用 content='主表'（external content）+ 触发器：省掉一份正文副本；记得 INSERT INTO ft(ft) VALUES('rebuild') 可在不一致时重建。
  6. 只要「哪些文档包含这些词」，用 detail=none：索引体积降到 25%，但别指望短语查询。
  7. 前缀搜索多就加 prefix='2 3'，只在「短前缀查询频繁」时才值得（体积×2.4）。
  8. 模糊/子串/LIKE 需求用 trigram，注意 2 字符查询无效、索引约 3.7 倍。
  9. 中文用 trigram 或 ICU，默认 unicode61 对 CJK 等于「整段一个词」。
  10. 默认搜索所有列；要限定列写 MATCH '{body} : 词'，否则书名/标题里的词会污染结果集（实测 whale 从 610 篇变成 1,614 篇）。
  11. 排序用 ORDER BY rank（等价于 bm25() 的负分），但记得排序有成本，候选多时先 LIMIT 或加列过滤缩小集合。
  12. 定期自检：INSERT INTO ft(ft, rank) VALUES('integrity-check', 1) 会重算并比对索引与正文的一致性。
